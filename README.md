# ВышКат — учёт парка кикшеринга

Консольное приложение для учёта техники и вещей сервиса кикшеринга «ВышКат».
Написано на Go с соблюдением принципов SOLID, внедрением зависимостей (DI) через
контейнер `go.uber.org/dig` и покрытием юнит-тестами.

## Запуск

Требуется Go 1.25.

```
go mod tidy          # подтянуть зависимость dig
go run .             # интерактивный режим, команды вводятся с клавиатуры
```

Прогон готового сценария из файла (ввод отделён от логики, см. ниже):

```
go run . < demo.txt
```

Тесты и покрытие:

```
go test ./...
go test -cover ./...
```

## Команды и параметры

Каждая команда вводится отдельной строкой: имя команды, затем аргументы через
пробел. **Наименование не должно содержать пробелов** (используйте дефис:
`Велосипед-городской`) — ввод разбивается по пробелам.

| Команда | Параметры | Описание |
|---|---|---|
| `-help` | — | список команд |
| `-add-transport` | `<вид> <имя> <инв.номер> <простота> [энергия]` | добавить транспорт (сначала техосмотр) |
| `-add-item` | `<вид> <имя> <инв.номер> [энергия]` | добавить вещь на баланс |
| `-count` | — | число единиц на балансе |
| `-total-energy` | — | суммарный суточный расход энергии (кВт·ч) |
| `-beginner-amount` | — | транспорт для новичков (простота ≥ 6), отсортирован по номеру |
| `-list` | — | вся техника и вещи с инвентарными номерами |
| `-exit` | — | выход |

Параметры подробно:

- **вид транспорта** (`-add-transport`): `bike`, `scooter`, `ebike`, `escooter`.
- **вид вещи** (`-add-item`): `helmet`, `dockstation`, `chargingcabinet`.
- **имя** — строка без пробелов.
- **инв.номер** — формат «слово-число», например `B-1`, `ES-12` (проверяется техосмотром).
- **простота** — целое 1–10 (при ≥ 6 устройство подходит новичкам).
- **энергия** — вещественное число (кВт·ч). Указывается только у электрических
  видов: `ebike`, `escooter`, `chargingcabinet`. У остальных аргумент можно не
  указывать — он игнорируется.

Примеры добавления транспорта и items:

```
-add-transport bike Велосипед-городской B-1 8
-add-transport escooter Электросамокат ES-1 6 0.6
-add-item helmet Шлем H-1
-add-item chargingcabinet Зарядный-шкаф C-1 2.0
```

## Архитектура

Три пакета, зависимости направлены в одну сторону `cli → service → domen`:

- **`internal/domen`** — доменная модель: интерфейсы и конкретные устройства.
- **`internal/service`** — бизнес-логика: парк (`Park`) и центр техосмотра
  (`ServiceCenter`). Зависит только от `domen`.
- **`internal/cli`** — интерактивный слой (`ConsoleApp`): чтение команд и вывод.
  Зависит от `service`.
- **`main.go`** — собирает всё вместе через DI-контейнер.

### Доменная модель

Общие поля вынесены во встраиваемые структуры (композиция вместо наследования):

- `baseUnit` name + invNum — даёт методы `Name()` и `InventoryNumber()`;
- `electric` dailyEnergy — даёт `DailyEnergy()`;
- `vehicleBase` = `baseUnit` + simplicity — даёт ещё `Simplicity()`.

Конкретные типы собираются из этих блоков:

| Тип | Inventoried | Transport | EnergyConsumer |
|---|:---:|:---:|:---:|
| `Bike`, `Scooter` | + | + | — |
| `EBike`, `EScooter` | + | + | + |
| `Helmet`, `DockStation` | + | — | — |
| `ChargingCabinet` | + | — | + |

## Принципы SOLID

### S — Single Responsibility (единственная ответственность)

У каждого типа одна причина для изменения:

- `domen`- описание устройств и их характеристик;
- `ServiceCenter` прохождение техосмотра;
- `Park` хранение items и ведение учета (BeginnerAmount, TotalEnergy, All, Count);
- `ConsoleApp` чтение ввода и печатать в вывод;

### O — Open/Closed (открытость/закрытость)

Система открыта для расширения, но закрыта для изменения. Виды устройств
создаются не через `switch`, а через **реестр конструкторов** —
`map[string]<transportFactory/itemFactory>` в `internal/cli/registration.go`. Чтобы добавить новый вид
транспорта, нужно создать новую структуру в `domen` и дописать **одну строку** в
реестр. Код приёма, отчётов и разбора команд при этом не меняется — то есть он
закрыт для модификации.

### L — Liskov Substitution (подстановка Лисков)

Любой конкретный тип можно использовать там, где ожидается интерфейс, не ломая
работу. `Park` и `ServiceCenter` работают с `Transport`/`Inventoried`, не зная
конкретного типа. Отчёт по энергии опирается на проверку интерфейса
(`u.(EnergyConsumer)`), а не на перечисление конкретных типов, поэтому новый тип
подставляется без правок. Тот же принцип позволяет в тестах подставить
`FakeServiceCenter` вместо `DefaultServiceCenter` — поведение `Park` не меняется.

### I — Interface Segregation (разделение интерфейсов) — применён наиболее явно

Вместо одного «толстого» интерфейса сделаны три маленьких
(`internal/domen/interfaces.go`):

- `Inventoried` — `Name()`, `InventoryNumber()`;
- `EnergyConsumer` — `DailyEnergy()`;
- `Transport` — встраивает `Inventoried` + `Simplicity()`.

### D — Dependency Inversion (инверсия зависимостей)

Модуль верхнего уровня (`Park`, политика учёта) зависит не от конкретного
`DefaultServiceCenter`, а от **абстракции** `ServiceCenter`. Конкретная
реализация передаётся снаружи, через конструктор `NewPark(checker ServiceCenter)`.
Благодаря этому:

- в проде подставляется настоящий `DefaultServiceCenter`;
- в тестах — `FakeServiceCenter`;
- контейнер сам решает, что именно подставить.

Именно инверсия зависимостей делает возможной подмену техосмотра в тестах.

## Внедрение зависимостей (DI)

DI реализован двумя уровнями:

1. **Внедрение через конструктор.** Зависимости не создаются внутри объекта, а
   передаются в него: `NewPark(checker)`, `NewConsoleApp(in, out, park)`.
2. **DI-контейнер `go.uber.org/dig`** в `main.go`. Контейнеру регистрируются
   алгоритмы создания каждого типа через `Provide`, а затем через `Invoke`
   запрашивается готовый `ConsoleApp` — контейнер сам занимается построением
   `ConsoleApp → Park → ServiceCenter` и создаёт объекты в нужном
   порядке. Важная деталь: провайдер отдаёт `ServiceCenter`, потому что `Park` просит интерфейс, а контейнер
   сопоставляет зависимости по типу.

Для трёх зависимостей контейнер избыточен, и граф можно собрать вручную; он
добавлен, чтобы соответствовать требованию «DI-контейнер» и показать работу с ним.


Пример реализации main.go без использования контейнера

```
center := service.NewDefaultServiceCenter(20.0)
park := service.NewPark(center)
consoleApp := cli.NewConsoleApp(os.Stdin, os.Stdout, park)

err := consoleApp.Run()
if err := app.Run(); err != nil {
    fmt.Fprintln(os.Stderr, "ошибка:", err)
    os.Exit(1)
}
```

## Где есть дыра/её объяснение (она легла на CLI)
`Park.AddItem` принимает любой `Inventoried`, в том числе транспорт. То есть
технически транспорт можно добавить через `AddItem`, минуя техосмотр, — это
ослабляет гарантию «весь транспорт проходит проверку». Приемлемо, потому что
разделение проведено на уровне CLI: команда `-add-transport` всегда гонит
устройство через техосмотр, а `-add-item` предназначена для вещей. Гарантия
держится на дисциплине вызывающего. Ужесточать (отклонять `Transport` внутри
`AddItem`) не стали, чтобы не усложнять модель без необходимости.
